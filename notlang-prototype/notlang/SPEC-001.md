# SPEC-001: Mizan v0.1 (minimal spec)

**Status:** Draft, matches the reference interpreter in `mizan/`.
**Companion to:** [PAPER-001](PAPER-001-ai-first-language.md) (this spec is "Phase 0" of its roadmap).

If this document and the interpreter disagree, the interpreter's test suite wins, and this document has a bug.

---

## 1. Scope

v0.1 defines the smallest useful core: one **function** per program, written as a typed graph, with declared effects and checkable contracts. It is meant to be generated by an AI and read through a viewer. It is not meant to be typed by hand, and it has no comments, no formatting rules, and no syntax.

Not in v0.1: user-defined function calls, loops or recursion, records as values, writes to the database, network, time, randomness, static proofs of contracts, and a binary encoding.

## 2. Program format

The v0.1 encoding is **JSON** (answer to open question 2 of the paper: structured text first, binary later). A program is one object:

| Key | Required | Meaning |
|---|---|---|
| `mizan` | yes | Must be the string `"0.1"` |
| `params` | yes | Object: parameter name to scalar type |
| `returns` | yes | Scalar type of the result |
| `effects` | yes | List of effects the function uses (section 6) |
| `nodes` | yes | Object: node id to node (section 4) |
| `out` | yes | Id of the node whose value is the result |
| `pre` | no | List of node ids, each must evaluate to `Bool` before the body runs |
| `post` | no | List of node ids, each must evaluate to `Bool` after the body runs |
| `label` | no | Human-facing name. Ignored by the interpreter and by hashing |

Unknown keys are errors. There is exactly one way to write each thing.

## 3. Types

Scalars: `Int` (JSON integer), `Money` (exact decimal), `Bool`, `Str`.
Derived (cannot be params or returns): `Rows<table>` and `List<T>` for numeric `T`.

- No implicit conversions. `Int` and `Money` never mix in comparison or addition.
- `Money` literals are JSON strings or integers (`"100.50"`, `0`). **JSON floats are rejected.**
- Tables come from the schema supplied with the database: `{table: {field: scalar type}}`.

## 4. Nodes and graph rules

A node is `{"op": ..., "in": [node ids], ...attributes}`. Edges are the `in` references, so nodes can be shared. The graph must be acyclic. Node ids carry no meaning (see section 8). Every node must type-check, even if unreachable.

## 5. Operations

| Op | Inputs | Attributes | Type rule |
|---|---|---|---|
| `const` | none | `type`, `value` | the literal's declared scalar type |
| `param` | none | `name` | the declared type of that param |
| `result` | none | none | the function's `returns` type. Only allowed under `post` |
| `add`, `sub` | 2 | none | `(Int, Int)` gives `Int`, `(Money, Money)` gives `Money` |
| `mul` | 2 | none | `(Int, Int)` gives `Int`; `(Int, Money)` or `(Money, Int)` gives `Money` |
| `eq`, `ne` | 2 | none | two scalars of the same type give `Bool` |
| `gt`, `ge`, `lt`, `le` | 2 | none | two `Int` or two `Money` give `Bool` |
| `and`, `or` | 2 | none | `(Bool, Bool)` gives `Bool` |
| `not` | 1 | none | `Bool` gives `Bool` |
| `if` | 3 | none | `(Bool, T, T)` gives `T` (scalar). Lazy: only the chosen branch runs |
| `db.scan` | none | `table` | `Rows<table>`. Effect `db.read` |
| `filter_eq` | 2: rows, value | `field` | keeps rows where `field == value`; value type must equal the field type |
| `pluck` | 1: rows | `field` | `List<type of field>` |
| `sum` | 1 | none | `List<Int>` gives `Int`, `List<Money>` gives `Money`. Empty sum is zero |
| `len` | 1 | none | `Rows` or `List` gives `Int` |
| `io.print` | 1 | none | scalar in, same scalar out. Effect `io.print` |

Evaluation is **demand-driven** from `out`, `pre` and `post`. Inputs are evaluated left to right and each node is evaluated at most once, so effects happen in a fixed order, at most once each. `and`, `or` and `if` do not evaluate inputs they do not need.

## 6. Effects

Known effects in v0.1: `db.read`, `io.print`. Reserved for later: `db.write`, `net.http`, `fs.read`, `fs.write`, `time.now`, `random`.

- The declared `effects` list must **exactly** equal the effects of the nodes reachable from `out`, `pre` and `post`. Using an undeclared effect is an error (`EFFECT_UNDECLARED`). Declaring an unused one is also an error (`EFFECT_UNUSED`), because extra permission is a risk and the author is a machine that can be exact.
- The host grants a set of effects at run time. If the function declares an effect that is not granted, it does not start (`EFFECT_DENIED`).

## 7. Contracts

- `pre` nodes are evaluated after arguments are bound and before the body. They may not depend on `result`.
- `post` nodes are evaluated after the body, with `result` bound.
- In v0.1 every contract is checked **at run time**. Static proof is future work (answer to open question 3: none of it is static yet).
- A failing contract stops the run with `PRE_FAILED` or `POST_FAILED`. The error carries the contract rendered as text, the bound arguments, and the result.

## 8. Identity (content addressing)

A function's identity is `sha256` over its canonical form: parameter types, return type, sorted effects, and the structural hashes of `out`, `pre` and `post`. A node's structural hash covers its op, attributes and the hashes of its inputs. So these do **not** change the hash: node ids, the order of keys, the `label`, the order of `pre`/`post` entries, and the spelling of a Money literal (`"0"` equals `"0.00"`). The short form is the first 8 hex digits, written `#a745dfa7`.

Not normalized yet: commutative operand order (`add(a, b)` and `add(b, a)` hash differently), and duplicate subgraphs.

## 9. Pipeline and errors

The interpreter runs these stages and stops at the first error:

1. **shape**: keys, ops, arity, references, acyclicity
2. **type**: every node, then return type and contract types
3. **effect**: declared vs used
4. **effect (grant)**: declared vs granted
5. **args**: bind and validate arguments
6. **contract / runtime**: `pre`, body, `post`

An error is data, not prose:

```json
{"stage": "type", "code": "TYPE_MISMATCH", "message": "...",
 "node": "res_ok", "detail": {"op": "ge", "input_types": ["Money", "Int"]}}
```

Codes: `NOT_OBJECT`, `MISSING_KEY`, `UNKNOWN_KEY`, `VERSION`, `BAD_PARAMS`, `BAD_RETURNS`,
`BAD_EFFECTS`, `UNKNOWN_EFFECT`, `BAD_NODES`, `BAD_NODE`, `UNKNOWN_OP`, `MISSING_ATTR`, `ARITY`,
`UNKNOWN_REF`, `CYCLE`, `TYPE_MISMATCH`, `BAD_LITERAL`, `UNKNOWN_PARAM`, `UNKNOWN_TABLE`,
`UNKNOWN_FIELD`, `RETURN_MISMATCH`, `RESULT_IN_BODY`, `RESULT_IN_PRE`, `CONTRACT_NOT_BOOL`,
`EFFECT_UNDECLARED`, `EFFECT_UNUSED`, `EFFECT_DENIED`, `BAD_ARGS`, `PRE_FAILED`, `POST_FAILED`,
`DB_ROW_INVALID`, `BAD_JSON` (CLI only).

## 10. The viewer

`mizan view FILE` renders a program for audit. The output is a debug view, not a source language, and it is never parsed back:

```
fn #a745dfa7  (partner_total)
  in:   pid: Int
  out:  Money
  fx:   [db.read]
  pre:  pid > 0
  post: result >= 0m
  body: sum(filter(db.invoices, partner == pid).amount)
```

`0m` is a Money literal. Shared subgraphs are printed inline each time they are used.

## 11. Answers to the paper's open questions (so far)

1. **Smallest useful node set:** the 22 ops above. The count is inflated by comparison variants. Everything else was left out on purpose.
2. **Encoding:** JSON first. A binary form comes after the semantics settle.
3. **Static contracts:** none in v0.1. Runtime checks only.
4. **Viewer for large graphs:** open. The v0.1 viewer inlines everything, which will not scale.
5. **Verifier as training signal:** open. The structured errors are designed for this, and the repair loop in `examples/repair_demo.py` is the first sketch.
